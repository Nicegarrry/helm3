# Wave 4 proposal: connect economy, supervision and the quality loop

This is a proposal for the next implementation wave. It does not change the original Brief, addendum, Map authority or spending rules. The original design remains authoritative in [design-original.md](design-original.md) and [design-addendum.md](design-addendum.md); GitHub issues and pull requests remain the live Map.

## Starting point

Wave 3 has accepted provider-free foundations:

- tracker observation and bounded GitHub transport;
- exact-head local gate execution and evidence classification;
- durable host ownership, scoped recovery, Pi fixture execution and uncertain-effect handling;
- one read-only operator projection, loopback API and CLI sharing the same snapshot.

The merged connected-control-plane line has a final 95-test provider-free fixture/demo result at PR #59 head `fa049ee6ad3497312bb49a268dbe7c4364a9b1c9`; PR #59 is merged. These are fixture and local-runtime outcomes. They do not prove live Pi OAuth, provider model access, autonomous dispatch, cross-provider interchange, or the complete feature scenario. Those outcomes remain open in the Map.

The recorded Map observation at 2026-09-15T08:23:56.450Z found 34 nodes and frontier issues #5, #7, #8, #10, #15 and #22. That projection is dated evidence, not a permanent frontier or an action authority.

## Proposed work lanes

1. **Model economy and reserves.** Inspect the pinned predecessor's verified accounting behaviours, then adapt model registry facts, resource pools, protected reserves and actual settlement to Helm 3 authority and attempt identities. Keep provider quota, subscription headroom and run-local reservations separate. Unknown values stay unknown. Add evidence for refusal at reserve and lease limits before any live access.

2. **Native supervisor and wakes.** Build the deterministic event supervisor around durable events and attempts. Coalesce duplicate wakes, reconcile only unambiguous transitions, retry only within a still-active lease and bounded attempt policy, and wake the frontier orchestrator for judgement. Expiry stops new spending while monitoring and evidence collection continue. No legacy fixed workflow or provider subprocess becomes Helm 3 authority.

3. **Fresh Map mutation.** Extend the native tracker adapter from observation to narrowly scoped, re-read-before-write Map changes. Bind every mutation to repository, issue identity, current revision and explicit authority; refuse stale or foreign targets. Preserve GitHub as Map authority and record exact receipts. A projection or old CLI result cannot authorize mutation.

4. **Quality and exact integration.** Run the complete gate → independent review → repair → exact-head integration loop against a real Helm 3 PR. Store command output, checked SHA, Standards/Spec verdicts and repair provenance. Integration must refuse moved heads, dirty worktrees, missing required review or stale evidence; workers prepare PRs and do not merge their own changes.

5. **Parallel access preparation.** Keep provider-free implementation and OAuth/live-access preparation independent. When the human is available, obtain only the explicitly bounded account approval and live probe authority then, with recorded limits and a stop condition. No elapsed time, baseline credential, fixture success or scheduled task grants consent automatically.

## Sequencing and acceptance

Economy facts and reserve enforcement should precede supervisor retries. Supervisor events, tracker mutation and the quality loop can then connect through the existing host and operator projections. Each lane remains independently reviewable and may proceed in parallel where its authority and input contracts are already accepted.

The next wave is evidenced only when a local run can expose honest economy state, coalesced supervisor wakes, a bounded fresh Map mutation receipt and a complete exact-head quality/integration receipt. A provider-free result must remain labelled as such. Live ACCESS, full Fable/Astra interchange, consultation, context lifecycle, cross-provider failover and the complete original acceptance scenario remain separate outcomes.

Follow-up waves should address native context and compaction, independent consultation, Fable/Astra interchange, cross-provider failover, calibration and full acceptance/legacy retirement after their prerequisites have evidence. This plan supplies order and boundaries; it is not a claim that those capabilities are built.
